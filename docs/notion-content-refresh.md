# Notion 内容更新与缓存刷新

Notion App 保存后，内容先同步到 Notion，再由本站在访问及 ISR 刷新时读取。文章必须满足数据库的发布条件。互动桌面的本地 JSON、图片和音频不属于这条同步链路。

## 部署

- 使用 Next.js 服务端部署（`npm run build` 后 `npm start`，或支持 ISR 的托管平台）。纯静态 `export` 不提供运行时内容刷新。
- 配置真实的 `NOTION_PAGE_ID` 及所需访问凭据。
- `NEXT_PUBLIC_REVALIDATE_SECOND=60` 控制默认数据缓存有效期和页面 ISR 间隔。这不是保存后固定 60 秒必达的承诺：请求触发、上游响应及多层缓存会影响实际延迟。
- 普通服务器、Docker 和托管部署均通过 `NODE_ENV=production` 识别生产环境。
- 显式 `ENABLE_CACHE=true` 可以开启缓存读取；文件、内存及 Redis 默认均使用有限有效期。旧的无过期时间文件缓存会被丢弃。
- 设置长随机 `REVALIDATION_TOKEN` 后才能使用主动刷新接口；令牌只保留在服务器或可信自动化中，不放入前端代码。

## 主动刷新

向博客服务发送 `POST /api/revalidate`，使用请求头 `Authorization: Bearer <REVALIDATION_TOKEN>`，JSON 请求体示例：

```json
{"paths":["/","/article/example"]}
```

请求会先清理本进程内存、当前实例文件缓存及当前站点命名空间的 Redis 数据，再逐个重新生成指定页面。文章内容修改时传文章地址；标题、发布状态、分类等修改还应包含首页及受影响的列表地址。路径必须使用实际页面路径，不带域名、查询参数或片段。单次最多 100 个地址。

`{"all":true}` 清理上述全部数据缓存并刷新首页，其他已经生成的页面仍按各自 ISR 间隔刷新；它不代表立即重新生成所有页面。需要立即刷新多个页面时明确传入 `paths`。

生成失败返回 HTTP 500 与逐页结果，不会伪报全部成功。`POST /api/cache` 只清理数据缓存，不重新生成页面，且必须另行设置 `CACHE_REVALIDATION_TOKEN`。

## 边界与验收

- 这里没有自动配置 Notion Webhook。普通编辑通过 ISR 读取；若需要保存后立即刷新，需要可信后端接收通知并调用上述接口。
- Redis 清理只扫描 `notionnext:v2:<站点 ID>:` 命名空间，不执行全库清空。升级后旧无前缀键不再读取，后续按其原有 TTL 过期。
- 多实例部署中，API 只直接清理接收请求实例的本地缓存；其他实例仍受有限 TTL 和其页面 ISR 缓存约束。需要所有实例即时一致时，应配置平台级页面失效或向各实例广播刷新。
- 验收时编辑一篇已发布文章，传首页与文章实际地址主动刷新，确认标题、正文及列表变化；再验证新文章发布和取消发布。不要把浏览器强制刷新等同于服务器清缓存。

相关回归测试位于 `__tests__/lib/cache/` 和 `__tests__/api/revalidate.test.js`。
